## QEMU bug found (upstream, debug path) [Source-read + 2 crashes]
HMP `x`/`x /i` of a guest address >= 0x80000000 on 32-bit PPC crashes QEMU:
hmp_memory_dump keeps the address as target_long (int32), it is sign-extended to
0xffffffffffff8500, and ppc_hash32_xlate indexes env->sr[eaddr >> 28] far out of range
(SIGSEGV in ppc_hash32_xlate+192; reports qemu-fc81963-2026-10-19-093950/094024.ips,
both on throwaway --snapshot VMs). Workaround: d3/gdbmem.py via -gdb tcp::1234.
Fix candidate (later, small): mask eaddr to 32 bits in the hash32 path or keep the
monitor address unsigned.

## Classification (VM) and next discriminator
Best supported: the emulated G4 (vCPU) is the limiting stage. CP and Metal render threads
are ~9-13% busy; flushes are 16/s with GPU wait ~5%; pixel area is a minor cost. Within the
vCPU: ~55-60% translated guest code, ~11% BQL, 4-23% guest idle, the rest QEMU helpers
(TB lookup, softmmu fills, hash32 page walks).
Competing explanations not yet excluded:
- Part of the "guest code" time could be the guest waiting in spin loops on GPU state
  (fences, ring space) rather than useful work; only a guest-PC profile separates them.
- Guest idle (4-23%) is waiting for something (likely GPU completion or vsync interrupts):
  latency there adds directly to frame time.
Next discriminator (ONE): an unbiased guest-PC profile. Debug-only patch: write
host_start/size -> guest_pc/flags (PR bit) per TB at translation; join with `sample`'s JIT
leaf addresses -> guest PC histogram, kernel vs user, then map to Doom 3 / ATI GL driver /
kernel / ATI kext. Not run yet: stopping here for review as the plan asks.
PowerBook half still to do (when it is powered on): same ablations + Shark/sample.

## Codex review (relay 2026-10-19) and corrected wording
- Classification, as Codex asks it to be phrased: "Limited sensitivity to primary pixel area;
  substantial cost associated with the 3D rendering path. Guest computation versus
  polling/driver/synchronization cost remains unresolved."
- skipRender removes guest GL/driver work, command production and host processing together;
  its 72% is not host-GPU time.
- CP / Metal thread busy figures are host CPU time only; they do not show the host GPU idle.
  "GPU wait" is flush wall time, not GPU utilisation.
- Denominator of the step 2 percentages: per-thread wall-clock samples from `sample`
  (1 ms ticks, every thread counted every tick whether on CPU or not), self time within the
  named thread. Thread figures overlap in time and must not be summed as frame cost.
- Codex approved the next step: a host-sampled guest-code profile (not "unbiased"), debug only.
- HMP: the explanation covers `x` (virtual, through ppc_hash32_xlate). `xp` is physical and
  bypasses it; only `x` was used in both crashes (x /40i 0xffff8560, x /64wx 0xffff8500).
